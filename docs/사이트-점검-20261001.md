# 사이트 자체 점검 (2026-10-01)

방법: 라이브(kicegg.com) 4개 페이지를 Lighthouse 모바일 기준으로 측정하고(홈, 시험 상세, 블로그 글, 회차 페이지), 저장소 전체 HTML 11,663개의 내부 링크·자산 참조를 검사했다. 측정 파일은 `tmp/lh/`(로컬).

## 1. 점수 요약 (모바일)

| 페이지 | 성능 | 접근성 | 권장사항 | SEO | LCP | CLS | TBT |
|---|---:|---:|---:|---:|---:|---:|---:|
| 홈(기출검색) | **75** | 100 | 100 | 100 | **5.1초** | 0 | 50ms |
| 시험 상세 | 90 | 96 | 100 | 100 | **3.5초** | 0 | 0 |
| 블로그 글 | 99 | 100 | 100 | 100 | 1.7초 | 0 | 0 |
| 회차 페이지 | 99 | 96 | 100 | 100 | 1.6초 | 0 | 0 |

- SEO·권장사항·레이아웃 이동(CLS)은 전부 만점/0이다. 접근성도 96~100.
- 문제는 **홈과 시험 상세의 LCP(첫 화면의 가장 큰 요소가 뜨는 시간)** 두 곳뿐이다. 구글 기준으로 2.5초 이내가 "좋음"이다.

## 2. 고칠 곳 (효과 큰 순)

### ① 시험 상세 LCP 3.5초 → 약 2초 목표 (작은 수정)
- 원인: LCP가 시험지 표지(흐린 미리보기 이미지)인데, 이 `<img>`를 JS(`exam.js`)가 뒤늦게 만들어서 이미지 요청이 **1.9초 늦게** 시작된다(LCP 시간의 54%).
- 해결: 상세 페이지 생성 때(`build-data.py`) 표지 `<img>`를 HTML에 직접 넣고 `fetchpriority="high"`를 달거나 `<link rel="preload" as="image">`를 추가한다. 시험 상세 1만 개 전체에 적용된다.
- 부작용 가능성: 낮음. 표지가 없는 시험은 그대로 둔다.

### ② 홈 LCP 5.1초 → 3초대 목표 (중간 규모)
- 원인: 첫 화면 결과 목록을 JS가 `senior.json`(전송 285KB, 5,527건)을 받아 그린다. 데이터는 0.9초에 도착하는데 그리는 데 약 4.4초가 걸린다(렌더 지연이 LCP의 86%). 화면 DOM이 2,058개로 많다.
- 해결 후보(효과 순):
  1. 처음에는 결과 20~30건만 그리고 나머지는 스크롤·더보기 때 그린다(DOM 2,058 → 약 500).
  2. 목록 JSON에서 문제지·정답 URL을 빼고(전체 크기의 상당 부분), 카드를 눌러 상세로 갈 때만 읽는다 → 285KB가 크게 줄어든다.
  3. 홈에 서버에서 미리 만든 첫 결과 목록(기본 필터)을 HTML에 넣는다. 이미 「최근 시험」 카드는 정적으로 있어서 같은 방식이다.
- 부작용 가능성: 중간. 검색·필터·정렬 로직(`app.js`, `state.js`)을 건드리므로 회귀 테스트가 필요하다.

### ③ 렌더 차단 CSS (홈 약 1.3초, 모바일 환산)
- `style.css`(19KB)와 Pretendard 글꼴 CSS가 렌더를 막는다. 해결: 글꼴 CSS는 `preload` 후 비동기로 읽고, `style.css`는 핵심 부분만 인라인한다. 글꼴 조각 파일이 12개(약 300KB)로 나뉘어 있어서, 첫 화면에 쓰는 조각만 `preload`하는 것도 방법이다.

### ④ 작은 정리
- JS·CSS를 압축하지 않아 합쳐서 약 15KB 낭비(`app.js` 등). CI의 `version-assets.py` 단계에 압축을 추가하면 된다. 안 쓰는 CSS 약 25KB도 있다.
- 홈의 흐린 미리보기 이미지 크기가 화면보다 커서 약 45KB 낭비(`uses-responsive-images`).
- Cloudflare 분석 스크립트(`beacon.min.js`)의 캐시 시간이 1일로 짧다(Cloudflare가 정하는 값이라 우리가 못 바꾼다).

## 3. 접근성
- 시험 상세·회차 페이지에서 `color-contrast` 경고가 나는 요소는 전부 **스포일러 블러 처리된 숫자**(`.spoil-val`, 의도적으로 흐림)다. 읽히면 안 되는 값이라 사용자 영향은 없지만, 점수가 96으로 깎인다. 블러 상태에서 `aria-hidden`을 주거나 대비 계산에 걸리지 않게 처리하면 100이 된다(우선순위 낮음).
- 키보드 이동(`skip-link`), 대체 텍스트(`aria-label`), 구조는 문제 없음.

## 4. 내용·구성에서 다듬을 곳
1. **404 페이지 메뉴에만 「블로그」가 없다**(다른 모든 페이지에는 있음). 한 줄 추가.
2. **상세 페이지에 스포일러 안내가 두 번 나온다**(등급컷 섹션과 공식 통계 섹션). 한 번만 표시하고 아래 섹션은 안내를 생략하는 게 깔끔하다.
3. **「준비 중」 화면**(특정 탭에 자료가 없을 때 "자료는 준비 중이에요")은 애드센스 입장에서 가치 없는 화면으로 보일 수 있다. 가능하면 이 화면이 노출되지 않게 탭을 숨기거나, 노출되더라도 `noindex`를 확인한다.
4. **개인정보처리방침·이용약관이 `noindex`**다. 심사 접근에는 지장이 없지만 사이트맵에서 빠져 있고 검색으로 안 보인다. 신뢰 신호로는 색인되는 쪽이 낫다는 의견도 있어 판단이 필요하다.
5. **문구 톤이 섞여 있다**(해요체·합니다체). 규칙과 구체적 제안은 `docs/사이트-문구-목록-20261001.md`에 있다.
6. 내부 링크 검사: 깨진 링크 없음. 404 페이지가 `/index.html` 같은 루트 절대경로를 쓰는 것만 검출됐고, 404는 어느 경로에서든 열려야 하므로 의도된 것이다. 누락된 CSS·JS·이미지 참조도 없다.

## 5. 이미 잘 돼 있는 것
- 모든 시험 페이지에 고유한 제목·설명·H1 1개, `BreadcrumbList` 구조화 데이터.
- 레이아웃 이동 0(광고 자리 미리 확보 구조 포함), HTML 용량이 가볍다(상세 38KB, 홈 28KB, gzip 시 6~9KB).
- 정적 HTML(JS 없이도 본문과 링크가 있음), 사이트맵·robots, CDN 캐시 설정.

2. ② 홈 결과 목록 렌더 줄이기 + ③ 글꼴·CSS 로딩 개선 (회귀 테스트 필요, 1~2일)

## 7. 적용 결과 (2026-10-01, 커밋 `bf70bb1`)

적용함
- ① 시험 상세 표지 `<img>`를 HTML에 직접 넣고 `fetchpriority="high"` + `<link rel="preload" as="image">`. exam.js 는 이미 있는 이미지를 두고 버튼만 붙인다. 표지 이미지 로드 지연 1.9초 → 0.78초(라이브 측정).
- ② 홈: 등급컷 표(`cuts.json`)를 `<head>`(site-prefs.js)에서 미리 요청하고, 첫 그리기가 최대 0.8초 기다려 한 번에 그린다(전에는 첫 그리기 뒤에 요청해 다시 그림). 시험 목록 쪽수(40건) 제한은 원래 있었다.
- ④ 404 메뉴에 블로그 추가, 상세의 중복 스포일러 안내 제거(등급컷 섹션이 있을 때), 개인정보처리방침·이용약관 `index` 허용 + 사이트맵 추가.
- 문구: `docs/사이트-문구-목록-20261001.md` 의 제안 대부분 반영(푸터·검색·오류·빈 화면·풀이 모드·달력·D-day·상세 한눈에 요약·공식 통계·자료 출처). 검색 결과용 메타 설명(시험·회차별)은 검색 노출 영향을 피하려고 그대로 뒀다.

미적용
- ③ 렌더 차단 CSS·글꼴 분할 로딩, JS·CSS 압축(CI 단계 추가 필요), 접근성 점수용 블러 숫자 처리.
- 홈 목록 JSON 용량 축소: 안 쓰는 필드를 빼도 압축 후 258KB → 237KB(8%)뿐이라 실익이 작았다.

측정 주의: 이후 라이브 Lighthouse 는 건드리지 않은 블로그·회차 페이지도 FCP 가 1.1~3.1초로 흔들려(이전 측정 1.6초) 시험 상세·홈의 점수 변화를 환경 노이즈와 구분하기 어렵다. 안정된 시간대에 재측정이 필요하다.
